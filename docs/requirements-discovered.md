# Discovered Requirements: livetrafik-ws-server
> Status: Discovered – requires validation by team

Reverse-engineered from code, config, workflows and tests on 2026-10-17 (HEAD `2e2049d`). Component layout, data flow and stack are in [ARCHITECTURE.md](ARCHITECTURE.md) and [STACK.md](STACK.md); build and run commands are in [KEY_DEVELOPMENT_COMMANDS.md](KEY_DEVELOPMENT_COMMANDS.md). This file records what the system must do and the rules it enforces, not how it is structured.

## System Overview

A single-instance relay on a Raspberry Pi 5. It holds one Supabase Realtime (Phoenix) WebSocket subscription per configured channel (default 4: `ul|sl` x `bus|train`) and re-publishes every `vehicles` broadcast unchanged to STOMP topic `/topic/{channel}`, so Supabase bills one Realtime subscriber instead of one per browser. It keeps an in-memory, remove-first delta cache per (region, type), served as a combined bus+train snapshot over REST. Every 30 s it reports status to the Supabase edge function `proxy-heartbeat`. Production runs the GraalVM native binary `/opt/livetrafik/trafik-websocket-server-linux-arm64` under systemd unit `livetrafik-ws.service`, on `*:9001`, published through a Cloudflare Tunnel (`.agent_temp/andthen-init-brief.md:21-27`). The only known consumer is Bussig (`../livetrafik`, hook `usePiLiveVehicles.ts`), which uses the proxy only when `app_settings.ws_source` selects it.

## Discovered Features

### Upstream subscription (Supabase Realtime)

- **REQ-D01**: On startup, open one WebSocket to `${supabase.url}?apikey=${supabase.anon-key}&vsn=1.0.0` and send one `phx_join` per channel on topic `realtime:{channel}` with `broadcast.self=false` – Evidence: `SupabaseRealtimeService.java:105-171`, `application.yml:11-15` – Confidence: High
- **REQ-D02**: Channel list is `{region}/vehicles/{type}` for every region in `supabase.regions` (default `ul,sl`) crossed with every type in `supabase.vehicle-types` (default `bus,train`); a non-blank `supabase.channel` CSV replaces the computed list entirely – Evidence: `SupabaseRealtimeService.java:56-63,273-286` – Confidence: High
- **REQ-D03**: Send a Phoenix `heartbeat` on topic `phoenix` every 30 s (first after 30 s) while the socket is open – Evidence: `SupabaseRealtimeService.java:173-189` – Confidence: High
- **REQ-D04**: On socket close, or on failure to construct the client, reconnect after a fixed 5 s delay with no backoff and no attempt limit; the reconnect re-runs the full `connect()` including all joins – Evidence: `SupabaseRealtimeService.java:127-132,143-146,266-271` – Confidence: High
- **REQ-D05**: Only frames with `event=broadcast` and inner `payload.event=vehicles` are processed; `phx_reply` is logged at DEBUG; all other events are ignored; unparsable frames are logged at ERROR with the full frame and dropped – Evidence: `SupabaseRealtimeService.java:191-215` – Confidence: High

### Downstream fan-out (STOMP)

- **REQ-D06**: Each `vehicles` payload is forwarded byte-for-byte as JSON (the inner `payload.payload` node) to `/topic/` + channel name with `realtime:` stripped, before any cache processing and regardless of whether it contains vehicles or removals – Evidence: `SupabaseRealtimeService.java:221-235,299-304` – Confidence: High
- **REQ-D07**: STOMP endpoints: `/ws` with SockJS fallback (Bussig connects to its raw-WebSocket transport `/ws/websocket`) and `/ws-native` plain WebSocket; destination prefix `/topic` served by the in-process simple broker; application prefix `/app` with no `@MessageMapping` handlers – Evidence: `WebSocketConfig.java:18-32`, `.agent_temp/andthen-init-brief.md:37` – Confidence: High
- **REQ-D08**: New STOMP subscribers receive no initial snapshot; they see only payloads broadcast after they subscribe – Evidence: no subscribe handler in `src/main`; `WebSocketConfig.java:18-22` – Confidence: High

## Implicit Business Rules

- **RULE-D01**: Payloads are deltas, never full snapshots: removals are applied first, then upserts keyed by `vehicle_id`, then stale cleanup; a vehicle both removed and present in the same payload ends up with the new data – Evidence: `VehicleCacheService.java:61-64`, `VehicleCacheServiceTest.java:32-85`, `.windsurf/rules/java-vehicle-broadcast.md:31-38`
- **RULE-D02**: Stale cleanup drops a vehicle whose `updated_at` (ISO-8601, else server receipt time) is older than `vehicles.cache.ttl-minutes` (default 5, not set in `application.yml`); it runs only when a payload arrives for that same (region, type), so a silent feed keeps serving its last vehicles indefinitely – Evidence: `VehicleCacheService.java:35,166-176,195-205`
- **RULE-D03**: A vehicle with `updated_at` already older than the TTL is inserted and removed in the same `applyDelta` call – Evidence: `VehicleCacheService.java:62-64`
- **RULE-D04**: Vehicles without a non-blank `vehicle_id` are skipped; null/blank removal ids are skipped; missing `vehicles`/`removed_vehicle_ids` are treated as empty; unknown JSON fields are ignored – Evidence: `VehicleCacheService.java:132-163`, `VehicleBroadcastPayload.java:19-38`, `VehicleCacheServiceTest.java:87-96`
- **RULE-D05**: Wire field name for removals is snake_case `removed_vehicle_ids`; `vehicleType` is camelCase – Evidence: `VehicleBroadcastPayload.java:22-29`, `.windsurf/rules/java-vehicle-broadcast.md:134`
- **RULE-D06**: Cache keys are trimmed and lowercased; STOMP topic names are not (they mirror the raw channel name) – Evidence: `VehicleCacheService.java:116-121`, `SupabaseRealtimeService.java:229`
- **RULE-D07**: Payload-level `region`/`vehicleType` win over the channel name; the channel name only fills blanks – Evidence: `VehicleBroadcastPayload.java:40-47`, `SupabaseRealtimeService.java:244`
- **RULE-D08**: Channel name parsing: 3+ slash segments → (seg0, seg2); exactly 2 → (seg0, no type) = combined region feed that is relayed but never cached; dash-separated legacy names → (part2, last part); single token → (token, `bus`); blank → (`ul`, `bus`) – Evidence: `SupabaseRealtimeService.java:306-326`
- **RULE-D09**: The REST snapshot always merges exactly `bus` and `train`, independent of `supabase.vehicle-types` – Evidence: `VehicleCacheService.java:82-87`
- **RULE-D10**: The `x-proxy-secret` header is sent only when `monitoring.heartbeat.secret` is non-blank; otherwise the heartbeat goes out without it (and the edge function answers 401 since 2026-10-17) – Evidence: `ProxyHeartbeatService.java:110-113`, `ProxyHeartbeatServiceTest.java:33-48`, `.agent_temp/andthen-init-brief.md:38`
- **RULE-D11**: Heartbeat interval cannot go below 15 s – Evidence: `ProxyHeartbeatService.java:63`
- **RULE-D12**: Only HTTP 200 counts as a successful heartbeat; anything else is logged at WARN with the response body, with no retry – Evidence: `ProxyHeartbeatService.java:85-96`
- **RULE-D13**: `SUPABASE_ANON_KEY` has no default; startup fails if it is unset – Evidence: `application.yml:13`, `SupabaseRealtimeService.java:53-54`, `ProxyHeartbeatService.java:35-36`

## Non-Functional Characteristics

- **Scale target**: load-test presets go to 200 concurrent clients over 5 min (`src/test/javascript/package.json:11`); no recorded result or SLO in the repo.
- **Latency**: measured, not bounded. Timer ranges imply expectations of ≤5 s Supabase-to-relay (`SupabaseRealtimeService.java:88`), ≤500 ms STOMP dispatch (`:95`), ≤10 ms outbound queue (`WebSocketMonitoringConfig.java:53`).
- **Outbound fan-out pool**: `clientOutboundChannel` executor core 16, max 64, queue 10 000. With `ThreadPoolExecutor` semantics threads beyond 16 are only created once 10 000 messages are queued (`WebSocketMonitoringConfig.java:32-37`). This pool uses platform threads; `spring.threads.virtual.enabled=true` (`application.yml:4-6`) applies to Tomcat and Spring-managed executors, not to this pool, the Java-WebSocket reader thread, or the hand-made `Executors.newSingleThreadScheduledExecutor` instances.
- **Concurrency model**: one Java-WebSocket reader thread calls `handleMessage` sequentially, so each (region, type) cache has a single writer; REST reads use `ConcurrentHashMap` weakly consistent iteration (`VehicleCacheService.java:30,130,178-182`).
- **Memory**: unbounded per-key maps; size bounded only by upstream vehicle count and the 5 min TTL. Each REST call deep-copies every cached vehicle twice (`VehicleCacheService.java:160,180`).
- **Availability**: single instance, single upstream socket, no persistence; a restart empties the cache until the next payload per key. Reconnect latency ≥5 s.
- **Security posture**: no authentication or authorization on STOMP, SockJS, `/ws-native`, REST or Actuator; origins `*` everywhere (`WebSocketConfig.java:27,31`, `VehicleController.java:17`). Exposure reduced to `health,info` in `2e2049d` but production still exposes 13 Actuator endpoints until redeployed (`.agent_temp/andthen-init-brief.md:54`).
- **Logging**: package level INFO (`application.yml:17-19`); the per-payload `[STOMP] vehicles update` line is DEBUG (`SupabaseRealtimeService.java:247`), so it does not appear in production.
- **Test coverage**: 5 cache unit tests, 3 heartbeat unit tests, 1 context test; nothing covers `SupabaseRealtimeService` parsing, channel mapping, reconnect, or STOMP delivery.

## Gaps & Uncertainties

Ordered by impact.

1. **[Fixed 2026-10-17, not deployed]** **Any STOMP client can publish to vehicle topics.** The simple broker routes client `SEND` frames whose destination starts with `/topic` straight to subscribers, and there is no inbound channel interceptor or auth. Anyone reaching the public tunnel can inject fake vehicles or removals into `/topic/ul/vehicles/bus` for all Bussig users. Evidence: `WebSocketConfig.java:18-21`, no `configureClientInboundChannel` in `src/main`. Confidence: High (documented Spring STOMP behavior; not exercised against production).
2. **[Fixed 2026-10-17, not deployed]** **Thread leak on every reconnect.** `scheduleReconnect()` creates a new non-daemon `ScheduledExecutorService` per call and never shuts it down (`SupabaseRealtimeService.java:266-271`); `startHeartbeat()` creates a new one per `onOpen` and overwrites the field without shutting down the previous one (`:173-174`), so old heartbeat loops keep running and each sends one Phoenix heartbeat per 30 s on the current client. Each Supabase disconnect therefore leaks at least 2 platform threads. `@PreDestroy disconnect()` closes the socket, which fires `onClose` → `scheduleReconnect()`, so a shutdown can schedule a reconnect on a non-daemon thread (`:328-336`).
3. **[Fixed 2026-10-17, not deployed]** **Delta ordering to clients is not guaranteed.** Broker-to-client messages go through the 16-thread outbound pool without `preservePublishOrder`, so two consecutive deltas on one topic can reach a client out of order, which defeats remove-first on the client side (ghost or missing vehicles). Evidence: `WebSocketMonitoringConfig.java:32-37`, `WebSocketConfig.java:18-22`. Confidence: Medium (documented Spring behavior; impact not observed).
4. **No channel-level recovery.** `phx_reply` status is only logged at DEBUG, and `phx_error`/`phx_close` for a channel are ignored. A rejected or server-closed channel stays dead while the socket is open, and `supabase_connected` still reports true. Evidence: `SupabaseRealtimeService.java:207-210,342-344`.
5. **Context test does not load the application.** `LivetrafikWsServerApplicationTests` declares a nested `@Configuration`, which Spring Boot uses *instead of* the `@SpringBootApplication` config. `contextLoads` therefore starts a context holding only a mock, and the unresolved `${SUPABASE_ANON_KEY}` never fails CI. Evidence: `LivetrafikWsServerApplicationTests.java:9-22`. Confidence: High.
6. **No native compile in CI.** RuntimeHints regressions surface only in the manually dispatched `native-arm64.yml`. Evidence: `ci.yml:27-28`.
7. **Deploy provenance of the running binary.** The Pi binary was installed 2026-10-12 10:11 local, after a `native-arm64.yml` build at 08:04 UTC that same day, but no `native-deploy.yml` run follows that build (last successful deploy 2026-02-09). How the binary got onto the Pi is open. `native-deploy.yml` also needs an interactive browser approval (`cloudflared access login`) and disables host key checking (`native-deploy.yml:36-58`). `deploy.yml` fails on every run because `actions/download-artifact@v4` without `run-id`/`github-token` only sees artifacts from its own run (`deploy.yml:25-29`). Artifacts expire after 30 days (`native-arm64.yml:50`).
8. **Heartbeat `version` is always `0.0.1-SNAPSHOT` in production** because `APP_VERSION` is unset and the value is not derived from `build-info` (`application.yml:30`, `MonitoringProperties.java:14`). `/admin/proxy` cannot tell builds apart.
9. **New subscribers start empty.** No snapshot on subscribe (REQ-D08) and Bussig is not known to call `/api/latest`. Unknown whether Bussig's producers send full lists periodically, which would mask this.
10. **Regions mismatch.** The proxy subscribes to `ul,sl`; Bussig documents only `ul` topics (brief item 3). Bussig migrations seed `sl` with `enabled=false` and broadcast only enabled regions (`../livetrafik/supabase/functions/fetch-vehicles/index.ts:637-646`), so `sl` channels are idle unless an admin enables the region. The live value is unverified.
11. **Hardcoded `bus`/`train` in the REST snapshot** ignores configured types (RULE-D09).
12. **Stale cleanup only runs on traffic for the same key** (RULE-D02); a stopped producer leaves vehicles visible over REST indefinitely.
13. **`connected_clients` can drift low.** `SessionDisconnectEvent` fires for sessions that never sent STOMP CONNECT, and the floor at 0 hides the mismatch (`WebSocketConnectionTracker.java:24-28`). Confidence: Medium.
14. **`trafik.stomp.outbound.queue` likely measures task submission, not queue wait.** A plain `ChannelInterceptor` on an executor channel gets `afterSendCompletion` once the task is submitted, before a worker runs it. Waiting time would need an `ExecutorChannelInterceptor` (`WebSocketMonitoringConfig.java:60-78`). Confidence: Medium.
15. **[Fixed 2026-10-17, not deployed]** **STOMP heartbeats are off.** The simple broker has no `TaskScheduler`/heartbeat value, so CONNECTED advertises 0,0 and the client's 10 s/10 s request (`../livetrafik/src/hooks/usePiLiveVehicles.ts:226-227`) negotiates to none. Bussig falls back on a 45 s client watchdog, and dead server-side sessions inflate `connected_clients`. Confidence: High (spring-messaging 6.2.15 source).
16. **Supabase latency metric depends on clock agreement** between the edge function and the Pi; negative skews are silently dropped (`SupabaseRealtimeService.java:255-264`).
17. **Purpose of `/ws-native`, the `/app` prefix, `release.yml` JAR releases, `K6LoadTest.js`** (defaults to `wss://localhost:8080/ws` and speaks no STOMP) and the legacy dash-name/2-segment channel parsing is unclear. No current caller is known.
18. **README is stale.** It describes a JAR on openjdk-17 under unit `trafik-ws`, `supabase.url` as an https base URL (code needs the full `wss` Realtime URL), logger `se.trafiklive`, `-Xmx` tuning, dash-named `SUPABASE_CHANNEL`, and legacy topics `/topic/vehicles-{region}` and `/topic/vehicles` that nothing produces by default (`README.md:57-115,284-343,389-392,496`).
19. **Lombok is in `compile` scope**, not `provided`/optional, so it ships in the JAR (`pom.xml:60-64`). The groupId is still `com.example` (`pom.xml:11`).
20. **Bussig downtime log is never opened.** `proxy-heartbeat` only closes `proxy_server_downtime_log` rows; nothing creates them since `proxy-health-check` was removed, so `/admin/proxy` downtime history stays empty. A Bussig-side fix, out of scope here.
